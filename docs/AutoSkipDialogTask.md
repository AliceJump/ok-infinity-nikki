# 剧情跳过与暗色选项跳过

`AutoSkipDialogTask` 是默认关闭的触发任务，每 0.3 秒检测一次。剧情选项采用键盘 `W`/`S` 导航、`F` 确认，不再点击聊天气泡；全局 `PostMessage` 输入后端不变。

- 必须同时检测到 `dialog_icon` 和 `skip_choose`，在右侧识别 `chat_icon`，依据每行文字长度与选项数量复用菜单指纹。灰色文字使用较低 HSV 亮度阈值参与**长度测量**，避免之前一行变暗导致整组选项无法识别。
- 单独分析每行文字的**亮/暗状态**。无法可靠测量时保持不操作；暗文字视为**已选过**，从候选中排除。对于未变暗的选项，使用原有菜单记忆起始位置循环选择；全部变暗则停止本菜单操作。
- 优先利用高亮行左侧白色 `F` 键帽的位置确定当前焦点。若没有识别出唯一焦点，只有首次进入菜单允许使用原先“默认第一项”的假设；在进行过 `W`/`S` 导航后，下一帧仍无法确认焦点则停止操作。
- 若当前焦点在目标选项上直接 `F`；焦点在目标上方发送一次 `S`，在下方发送一次 `W`。每轮最多发送一个键，按键前后保存截图；导航后在最多 3 次独立画面观察中核对焦点是否移动一行，期间不重复发送方向键。按 W/S 前后**比较选项行数和纵向位置**，而不是强求文本长度相同：服装亮片和高亮样式会污染长度计算。如果确认焦点已经移动到目标项，继续发送 `F`；若仍停留在原来**明确识别、且文字为亮色**的选项，则放弃轮换目标，确认当前高亮选项；焦点消失、变暗或菜单行位置变化时停止输入。
- `F` 后必须连续两帧检测不到 W/S 选项菜单才提交记忆；菜单持续可见达到五次检查时锁定，避免无响应导致循环发送。菜单连续两帧不再显示才解除锁定。
- 截图命名为 `dialog_ws_before_*`、`dialog_ws_after_*`、`dialog_ws_confirmed`、`dialog_ws_failed`，用于核对输入/截图。普通剧情没有 W/S、只有 `skip_f` 时，仍使用原先的 `F` 推进逻辑。

暗色判定来自选项字形（HSV 低饱和度、亮度门限），并非 OCR 或游戏内部的已完成标志。当前 1920×1080 夜间截图中，第一项为灰字、第二和第三项为白字；第二项的 `F` 提示表示**当前高亮的是第二项**，因此选择第二项时应直接发送 `F`，不应再多按一次 `S`。夜间/日间亮度、HDR 与其他 UI 皮肤可能影响阈值，须在游戏里确认；不可靠时应该停止而不是误选。暗色已选状态由每帧重新读取，不做永久性标记。本次暗文字识别改动不依赖模板资源调整；同分支另有并行的标注/子模块更新提交，发布前须单独验证其一致性。

实际日志回归：`2026-10-30 01:51:52` 报告「按下 W 后高亮行未移动到 1」，旧实现立即锁定直到菜单消失，导致选项界面无法自行恢复。现在先等待更多截图，如果方向键确实没有改变焦点但原高亮行仍为亮色，则只按一次 F 确认该行；若无法证明当前焦点为亮色，则仍保留失败停止，避免盲选。游戏实机是否接受 PostMessage 的 W/S/F 需要继续验证。

在用户提供的 `2026-10-30_01-51-51-577/815_dialog_ws_*` 截图中，W 前后 F 键帽分别位于约 `(1218,694)` 与 `(1219,634)`，实际移动一行；之前 `text_band_lengths()` 在背景/服装亮点干扰下把第一行宽度从约 13.31 测成 4.94 单位、第三行从约 28.75 测成 10.44 单位，导致 `_same_lengths` 拒绝了正确的导航。这两张图片证明 W 已生效，因此不得仅凭文字宽度变化判断高亮未移动。

## 模板匹配诊断与 ROI 统计

触发任务会向普通运行日志输出以 `DIALOG_MATCH ` 开头的单行 JSON（`log_info`）。包含每次真正执行的模板匹配：`dialog_icon`、`Y_N_left`（可选辅助信号，不作为所有对话菜单的前置条件）、`skip_choose`、`chat_icon`（多个聊天气泡会全部输出）、普通剧情的 `skip_f`。

- `frame: [width, height]` 是原始帧的像素尺寸；每个 `hits[]` 都记录模板 `name`、`confidence` 和 **归一化左上角坐标、宽高** `x/y/w/h`（对应像素 `x/W, y/H, w/W, h/H`；不是中心坐标）。未匹配的查询也保留 `count: 0`，便于统计误检与漏检。
- `scans[]` 每项记录实际搜索的 `template`、`threshold`、`limit`、`count` 和 `ms`；`total_match_ms` 为本轮真正执行的匹配耗时总和，不包含截图等待和图像亮度分析时间。
- `mode: explicit_roi` 代表 `roi` 为实际传入的归一化搜索范围；`mode: feature_anchor` 代表未显式传入 `box`，由 ok-script 在模板标注锚点及 variance 内搜索，`roi: null` 不代表全屏搜索。
- `find_one` 的门槛检查仍按 `limit: 1` 返回最高分匹配，以免为了诊断降低速度；`chat_icon` 使用 `find_feature` 的 `limit: all`，记录所有返回的选项图标。未执行的短路条件不构成一次匹配，不会伪装为“零命中”。
- `choices[]` 包含已分析菜单的 `focus`（从零开始、无法确定为 `null`）、暗字标记 `dimmed`、文本宽度单位 `text_width_units`、各行归一化中心 Y 坐标 `row_y`；`phase` 与 `input` 用于关联 W/S/F 导航。
- 检测集合、坐标（约 0.001 精度）或焦点/状态变化时输出一行；静止状态最多每 5 秒输出一次。发出输入、进入故障锁定时强制记录；同一帧相同模板/ROI 查询使用本轮缓存，避免重复做模板匹配。日志中的完整坐标以 5 位小数保存。

ROI 优化路线：先收集不同任务、天气、分辨率、选项数量下的 `hits`，计算每种模板左上角坐标与宽高的分位区间并加安全边距；对稳定的小图标采用固定局部 ROI，选项检测采用「先定位右侧候选区，再逐行搜索 F 提示和文字」的两阶段策略。不要凭单张截图收紧到固定 Y 坐标或删除无匹配日志；应对比优化前后 `ms`、漏检率与 16:9 缩放一致性。当前 PR 不自动改变已生效的检测 ROI。
